⚡ Exam-Eve Quick Guide — Datadog Fundamentals

This summary consolidates the most frequently tested topics across the 90 questions of the official certification. Memorize these tables before taking the practice exam.

1. Essential Datadog Agent Network Ports

Port Protocol Component / Purpose
8126 TCP Trace Agent (APM): Receives traces and spans sent by the application's instrumentation libraries.
8125 UDP DogStatsD: Ingests custom application metrics. Uses UDP because it is non-blocking with near-zero overhead.
5001 TCP Local IPC / CLI: Used internally for communication between the Agent daemon and the CLI (status, flare, etc.).
https://ip-ranges.datadoghq.com HTTPS Publishes all official Datadog CIDR blocks as JSON for configuring allowlists in corporate firewalls.

2. Most Tested Agent CLI Commands

Command What It Does (Exam Answer)
datadog-agent status First troubleshooting step: shows the status of running checks, credential errors and daemon health.
datadog-agent flare Packages logs and configs into a compressed archive, obfuscates sensitive passwords/keys and sends it automatically to Datadog Support.
datadog-agent check <name> Runs a single, isolated test of an integration (e.g., disk) without affecting the background daemon.
datadog-agent configcheck Prints all active, resolved YAML configurations loaded in the daemon's memory.
datadog-agent diagnose Validates network connectivity, DNS resolution and SSL certificates against the Datadog endpoints.
sudo systemctl restart datadog-agent Standard command to restart the Agent on modern Linux (required to apply changes to datadog.yaml).

3. API Key vs Application Key

Characteristic API Key Application Key
Ownership Belongs to the Organization. Belongs to a specific User.
Purpose Data ingestion by the Agent (metrics, logs, traces). Reading and managing via the REST API (dashboards, monitors, users).
If the user is disabled? Stays ACTIVE (avoids breaking monitoring). Is REVOKED immediately.
Default Limit Up to 100 active keys per organization. No strict shared limit.

4. Critical Aggregation, Dashboard and Monitor Concepts

  • Unified Service Tagging: Official standard made up of the env, service and version triad to correlate logs, traces and metrics.
  • Tag Rules: MUST start with an ASCII letter; maximum of 200 characters; boolean operators: AND, OR, NOT.
  • Space vs Time Aggregation: In avg:system.cpu.system{*} by {host}.rollup(avg, 3600), avg: and by {host} are space aggregation, while rollup() is time aggregation.
  • Cloning Out-of-the-Box Dashboards: Default integration dashboards are read-only; cloning them gives you access to Audit Events and permission control.
  • Mustache Syntax in Monitors: Uses {{#is_alert}} Alert! {{/is_alert}} and {{#is_recovery}} Recovered! {{/is_recovery}}.
  • Composite Monitor: Evaluates multiple monitors with boolean logic (e.g., A && B to fire only when disk and network are high together).
  • Muting a Host: Silences alerts by scheduling a Downtime window for planned maintenance.
  • Missing Data on Rare Errors: For metrics that only appear right before a crash, configure the monitor to fire when > threshold at least once and NOT notify on missing data.
  • Containers & Autodiscovery: Template variables use ascending order: %%port_0%% = lowest port, %%port_1%% = highest port. Log collection requires DD_LOGS_ENABLED=true.
