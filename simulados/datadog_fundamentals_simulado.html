⚡ Guia Rápido de Véspera de Prova — Datadog Fundamentals

Este resumo consolida os tópicos mais cobrados nas 90 questões da certificação oficial. Memorize essas tabelas antes de fazer o simulado.

1. Portas de Rede Essenciais do Datadog Agent

Porta Protocolo Componente / Finalidade
8126 TCP Trace Agent (APM): Recebe traces e spans enviados pelas bibliotecas de instrumentação da aplicação.
8125 UDP DogStatsD: Ingestão de métricas customizadas de aplicações. Usa UDP por ser não bloqueante e ter overhead quase nulo.
5001 TCP IPC Local / CLI: Usada internamente para comunicação entre o daemon do Agent e a CLI (status, flare, etc.).
https://ip-ranges.datadoghq.com HTTPS Publica em JSON todos os blocos CIDR oficiais do Datadog para configuração de allowlists em firewalls corporativos.

2. Comandos CLI mais Cobrados do Agent

Comando O que faz (Gabarito da Prova)
datadog-agent status Primeiro passo de diagnóstico: exibe status de checks ativos, erros de credenciais e integridade do daemon.
datadog-agent flare Empacota logs e configs em arquivo compactado, ofusca senhas/chaves sensíveis e envia automaticamente ao Suporte Datadog.
datadog-agent check <nome> Executa um teste isolado e único de uma integração (ex: disk) sem afetar o daemon de segundo plano.
datadog-agent configcheck Imprime todas as configurações YAML ativas e resolvidas na memória do daemon.
datadog-agent diagnose Valida conectividade de rede, resolução de DNS e certificados SSL com os endpoints do Datadog.
sudo systemctl restart datadog-agent Comando padrão para reiniciar o Agent no Linux moderno (necessário para aplicar mudanças no datadog.yaml).

3. API Key vs Application Key

Característica API Key Application Key
Propriedade Pertence à Organização. Pertence ao Usuário específico.
Finalidade Ingestão de dados pelo Agent (métricas, logs, traces). Leitura e gerenciamento via API REST (dashboards, monitores, users).
Se o usuário for desativado? Permanece ATIVA (evita quebrar o monitoramento). É REVOGADA imediatamente.
Limite Padrão Até 100 chaves ativas por organização. Sem limite estrito compartilhado.

4. Conceitos Críticos de Agregação, Dashboards e Monitores

  • Unified Service Tagging: Padrão oficial composto pela tríade env, service e version para correlacionar logs, traces e métricas.
  • Regras de Tags: OBRIGATÓRIO iniciar com letra alfabética ASCII; máximo de 200 caracteres; operadores booleanos: AND, OR, NOT.
  • Agregação Espacial vs Temporal: Em avg:system.cpu.system{*} by {host}.rollup(avg, 3600), o avg: e by {host} representam agregação espacial, enquanto rollup() representa agregação temporal.
  • Clonagem de Dashboard Out-of-the-Box: Dashboards padrão de integrações são read-only; ao cloná-los, você ganha acesso a Eventos de Auditoria (Audit Events) e controle de permissões.
  • Sintaxe Mustache em Monitores: Usa {{#is_alert}} Alerta! {{/is_alert}} e {{#is_recovery}} Recuperado! {{/is_recovery}}.
  • Composite Monitor: Avalia múltiplos monitores com lógica booleana (ex: A && B para disparar só se disco e rede estiverem altos juntos).
  • Mute de Host: Silencia alertas agendando uma janela de Downtime para manutenção programada.
  • Missing Data em Erros Raros: Para métricas que só aparecem antes de um crash, configure para disparar > limite pelo menos 1 vez e NÃO notificar em dados ausentes (missing data).
  • Containers & Autodiscovery: Variáveis de template usam ordenação crescente: %%port_0%% = porta mais baixa, %%port_1%% = porta mais alta. Coleta de logs exige DD_LOGS_ENABLED=true.
